# Format Specifications

This document describes the exact data formats used by zap-squad, from editor output to WASM rendering.

## Overview

```
Editor (MapEditor) → Level JSON → WASM Adapter → Sprite Lookup → Render
                                       ↑
Manifest.json ──────────────────────────┘ (tile definitions)
```

## 1. Level JSON Format (Editor Output)

Saved by MapEditor to `public/mods/levels/{name}.json`:

```typescript
interface MapFile {
  levels: LevelData[];
}

interface LevelData {
  identifier: string;       // Level name (e.g., "test_map")
  pxWid: number;           // Width in pixels (e.g., 2048)
  pxHei: number;           // Height in pixels
  layerInstances: LayerInstance[];
}

interface LayerInstance {
  __identifier: string;    // "Tiles", "Entities"
  __type: string;          // "Tiles", "Entities"
  __gridSize: number;      // 128 (always 128px tiles)
  gridTiles?: GridTile[];
  entityInstances?: EntityInstance[];
}

interface GridTile {
  px: [number, number];    // Position [x, y] in pixels (grid-aligned)
  t: number | null;        // VARIATION SEED (NOT the sprite index!)
  src: string;             // Tile asset ID (e.g., "pamant", "river")
}

interface EntityInstance {
  __identifier: string;    // "Character" or "Object"
  px: [number, number];    // Position (center point)
  defId: string;           // Character/object definition ID
}
```

### Important: The `t` Field

The `t` field is a **variation seed**, NOT a direct sprite index. It's a random number assigned when the tile is placed, used to deterministically select a visual variation.

## 2. Tile Atlas Structure

All tile atlases are structured as grids of 128×128 sprites:

### Terrain Tiles (e.g., `pamant.png`)

```
Width:  cols × 128 (e.g., 256 = 2 columns)
Height: 9 × 128 = 1152 (always 9 rows)

Row 0: Base variations (cols 0 to variations-1)
Rows 1-8: Transition overlays (8 compass directions for blending)
```

### Path Tiles (e.g., `river.png`)

```
Width:  15 × 128 = 1920 (always 15 columns for connectivity)
Height: 9 × 128 = 1152 (always 9 rows)

Row 0: Connectivity variants (cols 0-14, based on neighbor bitmask)
Rows 1-8: Transition overlays
```

## 3. Sprite Index Calculation

### Terrain Tiles: Seeded Pseudo-Random

The MapEditor uses this algorithm to select variations:

```typescript
function getVariationFromSeed(seed: number, variations: number): number {
  const x = Math.sin(seed * 9999) * 10000;
  const rand = x - Math.floor(x);  // Fractional part (0 to 1)
  return Math.floor(rand * variations);
}

// Example: seed=55, variations=2
// x = sin(55 * 9999) * 10000 ≈ -5883.4
// rand ≈ 0.566
// result = floor(0.566 * 2) = 1
```

The Rust adapter replicates this exactly:

```rust
fn get_variation_from_seed(seed: u32, variations: u32) -> u32 {
    let x = (seed as f64 * 9999.0).sin() * 10000.0;
    let rand = x - x.floor();
    (rand * variations as f64).floor() as u32
}
```

### Path Tiles: Connectivity Bitmask

Path tiles (rivers, roads) use neighbor connectivity:

```
Bitmask: N=8, S=4, W=2, E=1

Examples:
- Isolated tile (no neighbors):     bits=0  → variation=0
- Vertical (N+S):                   bits=12 → variation=11
- Horizontal (W+E):                 bits=3  → variation=2
- Cross (all 4):                    bits=15 → variation=14
- Corner NE:                        bits=9  → variation=8
```

Formula: `variation = (bits == 0) ? 0 : (bits - 1)`

## 4. Manifest Formats

### manifest.json (Editor Format)

Source of truth for asset definitions. Contains tile variations and types:

```json
{
  "tiles": {
    "pamant": {
      "id": "pamant",
      "name": "PAMANT",
      "atlas": "tiles/pamant.png",
      "atlasWidth": 256,
      "atlasHeight": 1152,
      "spriteSize": 128,
      "variations": 2,        // Number of visual variations in row 0
      "hasTransitions": true
    },
    "river": {
      "id": "river",
      "variations": 15,       // Path tiles have 15 connectivity variants
      "hasTransitions": true
    }
  }
}
```

### assets.json (zap-engine Format)

Generated by `scripts/convert-manifest.js`, consumed by zap-engine:

```json
{
  "atlases": [
    { "name": "tiles_pamant", "path": "tiles/pamant.png", "cols": 2, "rows": 9 }
  ],
  "sprites": {
    "pamant": { "atlas": 16, "col": 0, "row": 0 },
    "pamant_0": { "atlas": 16, "col": 0, "row": 0 },
    "pamant_1": { "atlas": 16, "col": 1, "row": 0 },
    "pamant_2": { "atlas": 16, "col": 0, "row": 1 },
    ...
    "pamant_17": { "atlas": 16, "col": 1, "row": 8 }
  }
}
```

Sprite index formula: `index = row * cols + col`

## 5. Data Flow

1. **MapEditor** paints tiles with random seeds (`t` field)
2. **MapEditor** saves level JSON with GridTile data
3. **WasmGame** loads manifest.json → sends to WASM via `reload_game_manifest`
4. **WasmGame** loads level JSON → sends to WASM via `load_level`
5. **WASM AssetGateway** parses tile definitions from manifest
6. **WASM AssetGateway** computes sprite_index for each tile:
   - For terrain: `get_variation_from_seed(seed, variations)`
   - For paths: `calculate_path_connectivity(neighbors)`
7. **WASM** looks up sprite `{asset_id}_{sprite_index}` in assets.json
8. **zap-engine** renders the sprite at the tile position

## 6. File Locations

```
ui/web/
├── public/
│   ├── assets/
│   │   ├── manifest.json     # Editor format (source of truth)
│   │   ├── assets.json       # zap-engine format (generated)
│   │   ├── tiles/*.png       # Tile atlases
│   │   └── characters/*.png  # Character atlases
│   ├── mods/
│   │   ├── levels/*.json     # Saved levels
│   │   ├── tiles/*/          # Modded tile definitions
│   │   └── characters/*/     # Modded character definitions
│   └── pkg/
│       └── zapsquad_wasm.*   # Built WASM module
└── scripts/
    └── convert-manifest.js   # Generates assets.json from manifest.json
```

## 7. Regenerating assets.json

When tile atlases or manifest.json changes:

```bash
cd ui/web
node scripts/convert-manifest.js
```

This reads `public/assets/manifest.json` and generates `public/assets/assets.json`.
